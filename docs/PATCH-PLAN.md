**عدم** إضعاف الحماية من الـ CW المزيّفة.

الترتيب مقصود: كل مرحلة تُختبر قبل الانتقال للتالية.

## المرحلة 2 — جعل الفلاتر قابلة للضبط لكل profile (جوهر الحل)

المشكلة أن `acceptDCW()` قرار شامل لا يعرف أي profile. الحل: تمرير
`struct cardserver_data *cs` إليه.

```c
/* التوقيع الجديد */
int acceptDCW_cs(struct cardserver_data *cs, uint8_t *data);
```

خيارات جديدة في `multics.cfg`:

```
DCW FILTER CHECKSUM: ON      # ON = السلوك الحالي (افتراضي، بلا تغيير)
DCW FILTER CHECKSUM: OFF     # لقبول الباقات ذات checksum غير قياسي
DCW FILTER REPEAT: ON        # ON = السلوك الحالي (افتراضي)
DCW FILTER REPEAT: OFF       # لإيقاف isbadDCW على الباقات المتضررة
DCW FILTER FAKECW: ON        # رفض صريح لنمط XOR 0xF0 + تسجيله في اللوغ
```

**مهم:** القيم الافتراضية = السلوك الحالي تماماً، فلا يتفاجأ أحد بعد الترقية.
المشرف يفتح الخيار **للـ profile المتضرر فقط**.

الأثر: 16 موضع استدعاء (`grep -rn acceptDCW *.c`) تحتاج تمرير `cs`.
في `cli-*.c` المتغيّر `cs = ecm->cs` متاح أصلاً في نفس النطاق.

## المرحلة 3 — إصلاح تسميم `SID_FILTER` (أخطر سبب للاستمرار)

المشكلة في `main.c:1774` (`cardsids_update`): الرصيد كان يتجمّد عند
`-100` ولا يرتدّ. **أُغلقت في TASK 3.13 (2026-09-26، D43):** النجاح عند
الأرضية يعيد الرصيد إلى 0، لا إلى `-90` كما في المقترح أدناه — التصفير
إلى 0 هو ما يفعله الفرع السالب فوق الأرضية أصلاً، و`-90` يبقى مستبعداً
ما دام `MAXFAILED` أقل من 100. مواضع العقوبة لم تُلغَ.

```c
/* مقترح: السماح بالارتداد البطيء بدل التجميد */
if ( sidata->val <= -100 ) {
	if (val > 0) sidata->val = -90;   // نجاح واحد يفتح الباب من جديد
	return 1;
}
```

بالإضافة إلى: **عدم معاقبة البطاقة** عندما يكون سبب الرفض فلتر الخادم نفسه
(`isbadDCW`/`checksumDCW`) وليس رفض البطاقة — لأن الذنب ذنب الفلتر لا البطاقة:

```c
if (!acceptDCW_cs(cs, dcw)) {
	srv->ecmerrdcw++;
	/* لا cardsids_update(-1) هنا إذا كان الرفض من الفلتر */
	...
}
```

## المرحلة 4 — تشخيص بدل التخمين

إضافة صفحة/أمر يُظهر **لماذا** رُفضت CW، بدل اللوغ الصامت الحالي:

* `telnet> dcwstats` — عدّادات الرفض حسب السبب
  (`checksum` / `repeat` / `null` / `badlist` / `fakecw`)
* صفحة ويب `/dcwrej` تعرض لكل `caid:prov:sid` عدد الرفض حسب السبب
* خيار `DCW DEBUG REJECT: ON` يسجّل كل رفض مع السبب

هذا يحوّل «باقة سوداء، لا أعرف لماذا» إلى رقم محدد في دقيقة.

## المرحلة 5 — تحديث البنية (اختياري، بعد استقرار ما سبق)

* `poll()` → `epoll()` في بقية المستمعين (r99 بدأها)
* فصل `httpserver.c` (7393 سطراً) عن منطق العمل
* بناء متعدد المنصات نظيف (CMake) بدل 20 فرع `ifeq` بمسارات مطلقة
  مثل `/opt/STM/STLinux-2.4/...`
* `-Wall` نظيف: حالياً عشرات التحذيرات الحقيقية (قراءة ما بعد نهاية المصفوفة
  في `md5.c` مثلاً)

## ما لا أنصح به

* **حذف الفلاتر بالكامل.** الفحص أثبت أن `checksumDCW` هو ما يصدّ هجوم
  XOR 0xF0 الموصوف في changelog r107. حذفه يفتح الباب للـ CW المزيّفة
  (شاشة سوداء من نوع آخر + تسميم كاش الأقران).
* **ترقيع ثنائي r107 بدون مصدر.** المصدر العام r82a فقط، والفجوة 25 إصداراً.
  أي تصحيح يجب أن يكون على المصدر ليقبل الصيانة.
