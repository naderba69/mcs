## اكتشاف سادس (جديد) — `CACHE THRESHOLD` يعمل عكس التوثيق

الكود كما كان **قبل** الإصلاح — الفحص اليوم هو `cache_threshold_reached()` عند `clustredcache.c:1609`، داخل `cache_setdcw()` (تبدأ في 1496):

```c
cwdata->nbpeers++;

if (cwdata->status&DCW_ERROR) return DCW_ERROR;

// TEST for min Peers
if (cwdata->nbpeers!=cfg.cache.threshold) return DCW_ERROR | DCW_SKIP;
```

المقارنة `!=` بينما التوثيق يقول:

```
CACHE THRESHOLD: 3 # accept every DCW only if it is received from 3 or more peers
```

أي «3 **أو أكثر**». الكود يقول «**يساوي** 3 بالضبط».

**~~تحقّقت أن `DCW_SKIP` لا يفحصه أحد~~ — هذا كان خطأً، صُحّح في 2026‑09‑22:**

> كان بحثي محصوراً في `clustredcache.c` وحده:
> `grep -n "DCW_SKIP" clustredcache.c`. أمّا الفحص الفعلي ففي
> `srv-*.c` و`cli-*.c`، وهو **موجود في ستة مواضع** ويُستعمل استعمالاً صحيحاً:
>
> ```
> srv-cccam.c:979    if ( !(res&DCW_SKIP) ) cli->cacheex.badcw++;
> srv-camd35.c:300   if ( !(res&DCW_SKIP)) srv->cacheex.badcw++;
> srv-cs378x.c:433   if ( !(res&DCW_SKIP)) cli->cacheex.badcw++;
> cli-cccam.c:502    if ( !(res&DCW_SKIP) ) srv->cacheex.badcw++;
> cli-camd35.c:240   if ( !(res&DCW_SKIP)) srv->cacheex.badcw++;
> cli-cs378x.c:310   if ( !(res&DCW_SKIP) ) srv->cacheex.badcw++;
> ```
>
> أي أن CW تحت العتبة **لا** يُحسب ضد مصدره — وهو الصواب بموجب GR1/GR2:
> المصدر لم يخطئ، أرضية الإجماع لم تُبلغ بعد. وهذا أيضاً سبب بقاء عيب `!=`
> خفيّاً: عطّل الميزة دون أن يُنتج اتهاماً كاذباً.

النص الأصلي (خاطئ، محفوظ للتتبع):

```
$ grep -n "DCW_SKIP" clustredcache.c
282:#define DCW_SKIP     0x08
1437:	if (cwdata->nbpeers!=cfg.cache.threshold) return DCW_ERROR | DCW_SKIP;
```

مُعرَّف في 282 ومُعاد في 1437، ولا يوجد أي `& DCW_SKIP` في الشجرة.

**الأثر الفعلي** — وهذا مهم، لأن `DCW_CYCLE` يُضبط **بعد** هذا السطر:

| `CACHE THRESHOLD` | ماذا يحدث |
|---|---|
| 1 (الافتراضي، `config.c:270`) | أول تقرير `nbpeers==1` → يُقبل. **الخطأ مخفيّ** |
| 3 | التقرير الثالث `nbpeers==3` → يُقبل. يعمل بالصدفة |
| 3 + وصول تقارير مجمّعة | `nbpeers` يقفز 1→4، فيتخطّى 3 → **لا يُقبل أبداً** |

وعندما يُرفض، يعود قبل `cwdata->status |= DCW_CYCLE`، فتفشل كل المسارات
اللاحقة التي تشترط `DCW_CYCLE` (2119، 2135، 2153). المسار الوحيد الذي
ينقذه هو 2166 الذي يطلب **5 أقران** بشكل ثابت:

```c
if ( !(cwdata->status&DCW_CYCLE) && (cwdata->nbpeers>=5) ) {
```

أي أن CW ذات دورة غير معروفة، مع `CACHE THRESHOLD: 3`، تحتاج فعلياً
**5 أقران** لا 3.

**الإصلاح المقترح:** سطر واحد.

```c
if (cwdata->nbpeers < cfg.cache.threshold) return DCW_ERROR | DCW_SKIP;
```

**المخاطرة:** منخفضة جداً. مع `threshold=1` السلوك لا يتغيّر إطلاقاً
(`1 < 1` خطأ، كما `1 != 1` خطأ). الفرق يظهر فقط مع `threshold > 1`، وهناك
السلوك الجديد هو الموثّق.

## القرار 1 — هل نحيي `checkcycle()` كما هي أم نعيد كتابتها؟

الكود المعطّل (633–691) يعتمد على `cw1cycle`. **تحقّقت من مصدر هذه القيمة:**

* من `SID LIST` في الـ profile، الصيغة `sid:chid:ecmlen.cw1cycle`
  (`config.c:4103`) — أي أن `cw1cycle` **اختياري** في السطر.
* أو من ملف `FILE CHANNELINFO`، الصيغة `caid prov sid.cw1cycle "الاسم"`
  (`config.c:2075`) — وأيضاً اختياري.

والكود المعطّل آمن عند غياب المعلومة:

```c
if (cw1cycle==0x80) { ... }
else if (cw1cycle==0x81) { ... }
return 1;      // cw1cycle غير معروف -> اقبل
```

**رأيي:** نحييها كما هي. سببان:
1. منطقها سليم، والمشكلة كانت أنها داخل تعليق.
2. عند غياب `cw1cycle` ترجع 1، أي **بلا تغيير سلوك** للقنوات غير الموثّقة.

**لكن هنا بيت القصيد:** الفائدة صفر تقريباً إذا لم يكن `cw1cycle` معبّأً في
`SID LIST` أو `channelinfo`. لذلك السؤال الحقيقي ليس برمجياً:

> **هل عندك ملف `channelinfo` أو `SID LIST` فيه `.80` / `.81` لباقة 1884 وNLS؟**

إذا كان الجواب لا، فإحياء `checkcycle` لن يغيّر شيئاً عندك، والأولوية تنتقل
إلى السبب 3 و6.

## القرار 2 — تجميد `cardsids_update` عند `-100` — **أُغلق في TASK 3.13**

أُغلق في 2026-09-26 (D43): الأرضية سقف، والنجاح يعيد الرصيد إلى 0.
الخيار «ج» (عدم المعاقبة حين يكون الرفض من الفلتر) لم يُنفَّذ هنا —
مواضع `-1` كما كانت. السقف `+100` لم يُمس.

`main.c:508-518`. التعليق الموجود في الكود يكشف نيّة المؤلّف:

```c
else sidata->val +=val; // else a card that has decode success one time cannot return to decode failed
```

أي أنه **تعمّد** عدم السماح للبطاقة الناجحة بالعودة إلى الفشل. لكنّه لم
يتوقّع الحالة المعاكسة: بطاقة وصلت إلى `-100` بفعل فلتر الخادم نفسه، فصارت
محكومة نهائياً.

**ثلاثة خيارات:**

| الخيار | السلوك | المخاطرة |
|---|---|---|
| أ — ارتداد بطيء | نجاح واحد يرفع من `-100` إلى `-90` | اهتزاز محتمل: بطاقة سيئة تُجرَّب مراراً |
| ب — ارتداد بمهلة | بعد `-100` تُنتظر N ثانية قبل أي إعادة تقييم | أكثر أماناً، لكنه يحتاج مؤقّتاً |
| ج — عدم المعاقبة أصلاً | لا `-1` عندما يكون سبب الرفض فلتر الخادم لا البطاقة | **الأصح منطقياً** — الذنب ذنب الفلتر |

**رأيي: ج + أ معاً.** ج يمنع الوصول إلى `-100` ظلماً، وأ ينقذ من وصل إليها
قبل التحديث. لكن ج تتطلب معرفة **سبب** الرفض في `cli-*.c`، وهذا ما توفّره
العدّادات التي بنيناها — لذلك كانت المرحلة 4 هي الصحيحة للبدء.

## القرار 3 — هل نجعل `checksumDCW` قابلاً للإيقاف لكل profile؟

هنا أختلف مع الانطباع الأول. **لا أنصح بإيقافه**، للأسباب التالية:

1. الاختبار أثبت أنه هو ما يصدّ هجوم XOR 0xF0:
   ```
   [ ok ] XOR-0xF0 fake CW is rejected = 0
   ```
2. إيقافه على باقة يعني قبول **كل** ما يرسله أي peer لتلك الباقة، بما فيه
   الشفرات الخاطئة — وهذا بالضبط عرضك الحالي.
3. البديل الأدق موجود أصلاً: `CACHE THRESHOLD`. إذا اتفق N أقران مستقلون
   على نفس CW فهي صحيحة عملياً — بشرط إصلاح السبب 6 أولاً ليعمل كما هو
   موثّق.

**اقتراحي:** لا نُضيف `DCW FILTER CHECKSUM: OFF`. بدلاً من ذلك:
* نُصلح السبب 6 (السطر الواحد) فيعمل `CACHE THRESHOLD` كما هو موثّق.
* نُضيف `DCW FILTER REPEAT: OFF` فقط (لـ `isbadDCW`)، لأن رفض ثلاث بايتات
  متساوية هو الحكم الأقل أساساً في الفلتر كله، وهو الوحيد الذي يرفض مفاتيح
  صحيحة مؤكَّدة.

هذا يقلّص مساحة التغيير ويُبقي الحماية.

## القرار 4 — الترقيم والهوية

`common.h:20-21`:

```c
#define REVISION    82
#define REVISION_STR  "82"
```

و`multics -h` يطبع `Multi CardServer r82 - by evileyes`.

**اقتراح:** لا ننتحل رقم r107 (لا نملك مصدره، والفجوة 25 إصداراً).

**تحذير تحقّقت منه:** `REVISION` العددي **لا يجوز تغييره**. فهو يُرسل على
الأسلاك كحرفين فقط:

```c
// clustredcache.c:1070
buf[24] = 'r'; buf[25] = '0'+(REVISION/10); buf[26] = '0'+(REVISION%10);

// clustredcache.c:2123-2124
buf[2] = '0'+(REVISION/10);
buf[3] = '0'+(REVISION%10);
```

أي قيمة ≥ 100 تُكسر إلى حرفين خاطئين فتفسد مصافحة الأقران. لذلك:

```c
#define REVISION     82          // يبقى 82 -- متطلّب بروتوكول، ليس اختياراً
#define REVISION_STR "82-mcs1"   // نصّي فقط، يُستخدم في main.c:1364
```

`REVISION_STR` هو ما يطبعه `main.c:2638`:

```c
char pg[] = "Multi CardServer r"REVISION_STR" - by ";
```

فيظهر `Multi CardServer r82-mcs1` ونميّز بناءنا بوضوح بلا أي أثر على الشبكة.
